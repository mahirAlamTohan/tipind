# Security & privacy review — November 2026

**Scope:** the shipped tipind site (static export, 8,522 products), its build
pipeline, and the public GitHub repository behind it.
**Method:** manual code review, targeted dynamic testing of the exported site,
dependency and git-history backtesting, load testing, and a black-box pass
against the built output.
**Status:** assessment only. **No fixes were implemented as part of this
review** — every recommendation below is for the team to apply and then retest.

Read alongside [the threat model](./threat-model.md) (what is at stake),
[the data inventory](./data-inventory.md) (what PII exists and where),
[the remediation plan](./remediation-plan.md) (order of work) and
[the evidence log](./evidence.md) (every command and raw output).

---

## 1. Verdict

The application code is in better shape than most AI-generated Next.js
projects: **no HTML-injection sinks, no `eval`, no third-party scripts, no
cookies, no analytics, `credentials: "omit"` on the only network call, and a
consistent "never trust `localStorage`" pattern.** The attack surface really is
close to zero, as the architecture claims.

The risk that remains is **not in the React code**. It is in the seam between
the repository and the world:

1. A **live, unauthenticated Google Apps Script endpoint** that returns the
   source price sheet is committed to a public repository — and is present in
   two forks and in every historical commit (F-01).
2. **Nothing verifies the catalogue the browser downloads**, while the file is
   cached `immutable` for a year (F-05). Price integrity rests entirely on the
   Cloudflare and GitHub accounts.
3. **No Content-Security-Policy**, so the first supply-chain or deploy mistake
   gets full control of the page — including the ability to swap the Telegram
   handle buyers are told to pay (F-02).
4. **Buyer PII stays in `localStorage` indefinitely after an order** (F-03),
   and the checkout collects free-text notes that will inevitably contain
   health information, with no privacy notice (F-04).
5. **The order message can be forged trivially** by typing newlines into the
   notes field (F-06).

| Severity | Count | Findings                                 |
| -------- | ----- | ---------------------------------------- |
| High     | 1     | F-01                                     |
| Medium   | 5     | F-02, F-03, F-04, F-05, F-06             |
| Low      | 7     | F-07 … F-13                              |
| Info     | 3     | F-14 … F-16                              |
| Bugs     | 6     | B-01 … B-06 (non-security, mostly small) |

Severity is impact × likelihood **for this architecture**, not a generic CVSS
score. A finding that would be Critical on a banking app can be Medium on a
static catalogue, and a scanner that reports "missing CSP: High" is describing
the same thing this report calls Medium.

### If you only do three things

1. **Rotate and hide the refresh endpoint, then purge it from history** (F-01).
   This is the only genuine secret the project has.
2. **Add a CSP built from the real inline-script hashes** (F-02) and **verify
   the catalogue hash at runtime** (F-05). Together they close the "someone
   else can change what buyers see and who they pay" class.
3. **Clear saved checkout details when an order is finished** (F-03) and **put
   a short privacy notice at the point of collection** (F-04).

### What could not be tested from this environment

The review sandbox has **no outbound network access** beyond package and GitHub
APIs. Three checks therefore must be run by you; each is one command and is
listed in [the retest checklist](./remediation-plan.md#retest-checklist):

1. Whether `CATALOG_SHEET_URL` currently returns the sheet to an anonymous
   caller, and in what format.
2. The live header set and cache behaviour on
   `https://tipind.mahiralamtohan.workers.dev` (the local export is faithful,
   but Cloudflare can add or strip headers).
3. Whether the Worker has Cloudflare WAF/rate-limiting, and whether the
   `workers.dev` subdomain is the only hostname.

Also unverifiable with the available token: branch protection, Actions
permissions, secret-scanning and Dependabot alerts on the repository (GitHub
returned 403). These are listed as "verify manually" in F-07.

### What is explicitly out of scope

Accounts, authentication, sessions, cookies, payments, card data, databases,
server-side request handling, file uploads and APIs. **The app has none of
these.** Requests to review them would be answered by pointing at
[ADR 0001](../decisions/0001-static-export-on-cloudflare.md) and
[ADR 0004](../decisions/0004-messenger-order-handoff.md). The only server-side
component is Google's Apps Script, which is Google's code, not ours.

### F-01 · Live catalogue-refresh endpoint published in a public repository · **High**

**CWE-200 (Exposure of Sensitive Information), CWE-798 (Hard-coded Credentials)**

**Where**

- `.env.production:17` — `CATALOG_SHEET_URL="https://script.google.com/macros/s/AKfycb…/exec"`
- `.env.example:22` — the same **live** value, not a placeholder.
- `package.json` in history (commit `f89d8c5`) — the URL was once inline in the
  `catalog:build` script.
- Git history: **4 occurrences** across all commits; the value has never been
  rotated (only one distinct deployment ID ever appears).
- Repository is **public**, and **two forks** created on 2026-11-01 each still
  contain `.env.production` (604 bytes) with the same endpoint.

**The file argues its own innocence, and is half right.** Its header says
"Every `NEXT_PUBLIC_*` value is embedded in the exported site, so none of this
is secret." That is true — and it is why the XOR key and the phone number are
safe to publish. But `CATALOG_SHEET_URL` has **no `NEXT_PUBLIC_` prefix**: it is
the one value in that file that is _not_ shipped, and the reasoning in the
comment was applied to it by accident. `.gitignore` even un-ignores the file
deliberately (`!.env.production`), so it is tracked on purpose.

**How it is exploited**

The Apps Script deployment must be readable by an anonymous caller, otherwise
`npm run catalog:build` on a fresh machine could not work. So:

```bash
curl -sL "https://script.google.com/macros/s/AKfycb…/exec" | head -c 400
```

returns the live price list to anyone who has the URL — no login, no key, no
rate limit you control. A scraper only needs the repository, which is public
and indexed. Steps:

1. Find the repo (search for `tipind`, or the GitHub fork notice).
2. `git clone` or open `.env.production` in the web UI.
3. Fetch the endpoint on a schedule. You now have every row, every column,
   before the artifact is even rebuilt.
4. Optional: call it in a loop. Apps Script has daily quotas per account; the
   quota is yours, so exhausting it breaks **your** catalogue builds, not
   theirs.

**Impact**

- **Confidentiality:** every column in the sheet, including any not published
  in the artifact (cost, margin, supplier, stock notes, discontinued flags).
  Only you know whether such columns exist — if the sheet is exactly the
  published data, the marginal leak is smaller but still real: the masked
  artifact is a snapshot, the endpoint is live.
- **Business intelligence:** live prices and stock on demand, without waiting
  for a rebuild.
- **Availability:** quota exhaustion on the Apps Script project, which silently
  breaks `npm run catalog:build` at the worst moment.
- **Persistence:** deleting the file now does not help. The value is in 3
  commits, 2 forks, and every clone anyone has made.

**Remediation**

1. **Create a new Apps Script deployment** (Deploy → New deployment). Do not
   edit the old one; archive it. The new URL has a new ID, so the published one
   is dead.
2. **Stop publishing the URL at all.** Best: move the refresh into a GitHub
   Action that authenticates to Google with a service account and reads the
   sheet through the Sheets API; no public endpoint then exists. Cheap
   alternative: keep the web app but require a token
   (`?token=…` compared against a `PropertiesService` value) and store the
   token only in the CI secret store.
3. **Treat the sheet as confidential:** set sharing to specific people, not
   "anyone with the link". The endpoint is not the only path to the data.
4. **Untrack the file:** remove `.env.production` from git, drop the
   `!.env.production` exception in `.gitignore`, commit `.env.example` with
   placeholders only.
5. **Purge history** with `git filter-repo --path .env.production
--invert-paths`, force-push `main`, and ask GitHub Support to expire cached
   views. Understand that **forks keep the old objects**: rotation in step 1 is
   what actually protects you, the purge is hygiene.
6. **Add a pre-commit secret scanner** (`gitleaks` or `detect-secrets`) and
   turn on GitHub **push protection** so the next accidental commit is blocked
   rather than published.
7. **Check the two forks.** Their commits are authored with
   `mahiralamtohan@gmail.com` and were created minutes apart, so they look like
   your own alternate accounts — confirm that. If they are not yours, assume
   the endpoint is already in someone else's hands and rotate immediately.

**Done when**

- The old URL returns an error or a Google sign-in page, and the new one is
  used only by CI.
- `git grep -I "AKfycb"` returns nothing on the default branch **and** on
  `main`'s history (`git log -S AKfycb --oneline` is empty after the rewrite).
- `.env.production` is untracked; `.env.example` contains `your-deployment-id`.
- Push protection is on and a test commit containing a fake token is rejected.

**Residual risk:** anyone who cloned before the rotation still has a copy; that
copy becomes worthless the moment the deployment is archived.

### F-02 · No Content-Security-Policy, and four inline scripts per page · **Medium**

**CWE-693 (Protection Mechanism Failure), CWE-1021 (Improper Restriction of Rendered UI Layers)**

**Where** `public/_headers` sets seven headers (nosniff, `X-Frame-Options:
DENY`, referrer policy, HSTS, Permissions-Policy, COOP, plus cache rules) and
**no CSP**. `out/index.html` and `out/checkout/index.html` each contain **4
inline `<script>` blocks** (theme bootstrap 527 B, Turbopack runtime 243 B,
`__next_f` bootstrap 43 B, RSC payload ~9.4 KB) and 13 external scripts.

**Why it matters more here than the scanner score suggests**

There is no injection sink in the current code — no `dangerouslySetInnerHTML`,
`innerHTML`, `eval`, `new Function`, `document.write`, `postMessage`, and all
`target="_blank"` links carry `rel="noreferrer"`. So there is **no exploit path
today**, which is why this is Medium and not High.

What CSP buys is _blast radius_. The highest-value target on this page is not
the catalogue; it is **the sentence that tells a buyer where to send money**.
`siteConfig.contact.telegramUsername` and the email address are rendered from
configuration. A single malicious npm release, a compromised Cloudflare token,
or a future XSS in any dependency would let an attacker:

1. Replace `@tipind` with their own handle, and `shop@tipind.ru` with a
   lookalike.
2. Leave the header, layout and prices untouched, so nothing looks wrong.
3. Wait for buyers to send addresses and payment.

`X-Frame-Options: DENY` already blocks the classic clickjacking variant, and
there is no `frame-ancestors` fallback for browsers that ignore XFO (all modern
ones honour both, so this is belt-and-braces).

**How it is exploited** (once a script executes, which today requires a
supply-chain or account compromise)

1. Ship/obtain script execution in the page context.
2. `document.querySelectorAll('a[href^="https://t.me"]')` → rewrite the handle;
   same for `mailto:`.
3. Read `localStorage["tipind:checkout:v1"]` for the saved address and email
   (see F-03), and exfiltrate to any host — with no CSP, `fetch` to a third
   party is unrestricted.
4. Optionally rewrite displayed prices to bait a purchase.

**Impact** Depends entirely on step 1 happening. With CSP, a stolen package can
still run during the supply-chain window but cannot load a remote payload, cannot
exfiltrate to an attacker host, and cannot be injected via a future sink.

**Remediation**

1. Generate the policy **after** `next build`, because the inline hashes change
   on every build. A ~40-line post-build script can parse each HTML file under
   `out/`, hash every inline `<script>`, and emit per-path CSP entries into
   `_headers` (Cloudflare supports per-path rules; each page gets its own
   `script-src` list). Do not hand-write hashes.
2. Start from:

   ```
   default-src 'self';
   script-src 'self' 'sha256-…' 'sha256-…' 'sha256-…' 'sha256-…';
   style-src 'self' 'unsafe-inline';
   img-src 'self' data:;
   font-src 'self';
   connect-src 'self';
   manifest-src 'self';
   object-src 'none';
   base-uri 'none';
   form-action 'self';
   frame-ancestors 'none';
   upgrade-insecure-requests;
   report-to csp-endpoint;
   ```

3. **`style-src` needs `'unsafe-inline'`** unless you refactor: the pages carry
   **18 inline `style="…"` attributes** (cart width var, meter widths). Those
   are blocked by a strict `style-src`, and there are no inline `<style>` tags
   to hash. Allowing inline _styles_ does not permit script execution; keep
   `script-src` strict.
4. Add `Reporting-Endpoints` + `report-to` (or `report-uri`) pointing at a
   Cloudflare Worker or a third-party collector, and **watch it for a week**
   before enforcing. Roll out in report-only first if you prefer.
5. Keep `X-Frame-Options` as well; belt-and-braces costs nothing.

**Done when** `curl -sI https://…/` shows a `content-security-policy` with
`frame-ancestors 'none'` and no `unsafe-inline` under `script-src`; the site
renders identically in a fresh profile with the console open and **zero CSP
violations** on `/`, `/checkout/` and a 404; the theme toggle still works before
first paint (this is what the 527-byte inline script does — if it breaks, you
have hashed it wrongly).

**Residual risk:** `workers.dev` serves the site on a shared parent domain, but
that does not weaken CSP.

### F-03 · Buyer PII is kept in `localStorage` indefinitely after the order · **Medium**

**CWE-359 (Exposure of Private Information), CWE-212 (Improper Removal of Sensitive Information)**

**Where**

- `src/features/checkout/components/checkout-page.tsx:86-91` — `finish()` calls
  `clearCart()` and navigates home. It **does not** call `clearDetails()`.
- `src/features/checkout/checkout-store.ts:49-88` — the whole `details` object
  is persisted to `localStorage["tipind:checkout:v1"]` on every keystroke
  (`setItem` on each change), with no expiry.
- `src/features/checkout/components/details-form.tsx:348-357` — the only purge
  is the "Clear saved details" link, which the buyer must find and press.
- Reading is capped at 100,000 characters and every field is re-sanitised
  (`checkout-store.ts:15-47`) — good — but nothing deletes it.

**How it is exploited**

This is a privacy defect with several mundane exploitation paths, none of which
needs an attacker with skills:

1. **Shared or resold device.** The buyer orders on a family laptop, a work
   machine, or a phone they later sell. Anyone who opens `/checkout/` sees the
   full name, street address, city, postcode, email and any notes, pre-filled,
   because `skipHydration` restores them silently.
2. **Browser profile sync.** Chrome/Firefox sync `localStorage` to every signed-in
   device, so the address follows the buyer around.
3. **Any future script execution** (see F-02) reads it with one line:
   `localStorage.getItem("tipind:checkout:v1")`.
4. **Public terminal / library machine**: the value survives closing the tab.

The data is _also_ never deleted after it has served its purpose, so the site
holds PII it does not need — the definition of unnecessary retention.

**Impact** Disclosure of a home address and email, potentially with a note like
"please send to my mother's address, she has cancer" (see F-04). No payment
data is stored, and the cart is cleared correctly.

**Remediation**

1. **Call `clearDetails()` inside `finish()`** — one line, and it closes the
   common case. Do the same in any future "start over" path.
2. If you want the convenience of a pre-filled form for repeat buyers, make it
   **opt-in and time-limited**: a "remember my details on this device" checkbox
   (default **off**), stored only when ticked, with a 30-day expiry checked on
   read (`{ savedAt, details }`), and a visible "Forget me" control in the
   header or footer, not buried under the form.
3. Stop persisting on every keystroke; write on blur or before the message step.
   This also reduces the window in which a half-typed address exists on disk.
4. Add a small **"Stored on this device"** line next to the saved-details notice,
   explaining what is stored and how to delete it. You already have the
   "saved for next time" copy — tell the truth about where.
5. If a repeat order is important, store only `firstName`, `email` and `country`
   and re-ask for the address. Address is the sensitive part; an email is not.

**Done when** placing an order and returning to `/checkout/` shows an empty
form; `localStorage.getItem("tipind:checkout:v1")` is `null` after
`finish()`; the opt-in checkbox (if you add one) is unchecked by default and an
entry older than 30 days is discarded on read.

**Residual risk:** whatever is typed before the order is still on disk for the
duration of the session. That is acceptable if the retention is disclosed.

### F-04 · No privacy notice or consent, while collecting address and free-text health data · **Medium**

**CWE-359; GDPR Art. 5/6/9/13, UK GDPR, CCPA/CPRA, India DPDP Act 2023, NZ Privacy Act 2020, Australian Privacy Act 1988**

**Where** `src/features/checkout/components/details-form.tsx` collects first and
last name, email, company (optional), two address lines, city, region, postcode,
country, a payment-method preference and **a free-text notes box of up to 1,000
characters**. There is no privacy page, no notice, no consent, no retention
statement, and no way to request deletion. Search for `privacy` across `src/`
and `public/`: nothing. The only related copy is
`copy.details.savedNotice` ("saved on this device for next time"), which
describes a behaviour but gives no rights or retention.

Why the notes box is the sharp edge: people buying medicines will write "for my
diabetes", "my son's asthma inhaler", "no prescription, it's for my mother's
chemo". That is **special-category health data under GDPR Art. 9**, collected
incidentally, sent over Telegram, and stored on Google/Microsoft infrastructure
with no agreement and no stated basis. It is also unnecessary for quoting an
order.

**Who this matters to** The site ships to the US, UK, NZ and Australia. UK
buyers are in scope of UK GDPR; EU buyers (you do not restrict to the four
countries in the form, you restrict _shipping_, but nothing stops an EU buyer
from emailing) are in scope of GDPR; California residents are in scope of
CPRA; Indian operations are in scope of the DPDP Act. Even with low volume,
the obligations are the same shape: tell people what you collect, why, for how
long, and who else sees it; give them a way to have it deleted.

**How it is exploited** Not an attacker, an auditor or a customer: a buyer (or a
competitor) asks "what do you do with my address?", or a regulator asks for your
record of processing. There is currently nothing to show, and the answer "we
copy it into Telegram" is not a lawful-transfer story.

**Impact** Regulatory exposure (fines and, more likely, a complaint and a forced
clean-up), plus reputational damage that is disproportionate for a small shop.
No technical compromise is needed.

**Remediation**

1. **A one-page `/privacy` notice**, linked from the footer and from a line
   above the checkout form. It needs six things: who the controller is (legal
   name and contact), what is collected (list the fields), why (to quote and
   ship an order), where it goes (Gmail/Google Workspace, Telegram, WhatsApp —
   name them), how long it is kept, and how to have it deleted (an email address
   is enough). You do not need a lawyer for a page this short; you do need it to
   be true.
2. **Do not ask for health information.** Change the notes placeholder to
   "Delivery instructions only — please don't include medical details", and
   consider dropping the field to 200 characters. If someone needs to send a
   prescription, that belongs in the email thread, under a stated purpose.
3. **State the messenger hand-off explicitly** at the point where the buyer is
   told to send their address: "Sending your order shares your name, address and
   email with Telegram/your email provider."
4. **Set a retention rule** — e.g. "order messages are deleted from the inbox
   after 90 days, or when the order is closed" — and actually do it. Write it
   in the notice.
5. **Do not add analytics or a cookie banner you do not need.** Today the site
   sets no cookies and loads nothing from third parties, which is a genuine
   selling point; keep it that way (see F-14 and the positive controls in §5).

**Done when** `/privacy` exists, is linked from the footer and checkout, names
the messengers, gives a deletion contact and a retention period, and the notes
field no longer invites medical detail.

**Residual risk:** a notice does not make the messengers compliant; the team
still needs to delete messages on schedule.

### F-05 · The catalogue the browser loads is not authenticated, and is cached `immutable` for a year · **Medium**

**CWE-345 (Insufficient Verification of Data Authenticity), CWE-494 (Download of Code Without Integrity Check)**

**Where**

- `src/features/catalog/lib/load-catalog.ts:141-186` fetches
  `NEXT_PUBLIC_CATALOG_DATA_URL`, unmasks, gunzips, parses — with no integrity
  check of any kind. `parseCatalog` validates _shape_ (format version, tuple
  length, price bounds partially) but not _values_ and not _provenance_.
- `public/_headers:5-8` serves `/data/*.dat` with
  `Cache-Control: public, max-age=31536000, immutable`.
- The filename contains a content hash (`catalog.d50350bf.dat`), which is good
  hygiene, but the URL comes from configuration, so nothing forces the hash to
  match the bytes.

**How it is exploited**

There is no remote attacker path (same-origin fetch, TLS, HSTS). The realistic
paths all involve write access to the deploy chain:

1. **Compromised Cloudflare token or account** — the classic: a leaked API token
   or an over-scoped GitHub Action replaces `out/data/*.dat`. Every visitor now
   sees attacker prices, attacker product names, attacker everything. Nothing on
   the page notices.
2. **Compromised npm dependency in the build** — `scripts/build-catalog.mjs`
   transforms prices; a malicious transitive package can alter them at build
   time, and the hash will happily match because the file is hashed after
   tampering.
3. **Honest mistake with a long tail** — a bad build ships (wrong column mapped,
   prices ×100). The previous artifact is _still cached for a year_ on every
   device that visited, so even after you fix and redeploy, returning buyers keep
   seeing the wrong prices. `immutable` tells the browser never to revalidate.
4. **Deploy ordering** — the HTML and `.env.production` both reference
   `catalog.<hash>.dat`. If HTML goes live before the artifact (or a rebuild
   changes the name and the deploy is partial), buyers get a 404 that is
   _itself_ cached under `/data/` for a year. The UI handles the error
   gracefully, but they see no catalogue until they clear storage.

**Impact** Price integrity is the business. A manipulated price is a direct
loss (a buyer will hold you to the displayed price) and a trust event. The
year-long immutable cache turns any mistake into a multi-week support problem.

**Remediation**

1. **Cross-check the hash you already have in the filename.** The build script
   knows the digest; write it to an env var (`NEXT_PUBLIC_CATALOG_SHA256`) at the
   same time as the URL, and after `arrayBuffer()` compute
   `crypto.subtle.digest("SHA-256", bytes)` and compare. Mismatch → show the
   existing "catalog could not be decoded" state, do not render. This costs
   ~2 ms for 204 KB and turns "any write access can change prices" into "any
   write access must also change the HTML and rebuild".
2. Better, and cheap: **sign the manifest** — a `catalog.json` containing
   `{ url, sha256, builtAt, rowCount }` plus a detached signature (Ed25519 via
   WebCrypto, public key in the bundle), generated by the build. Overkill for
   now, but it is the end state if the catalogue ever becomes valuable.
3. **Fix caching:** `max-age=31536000, immutable` belongs on
   `/_next/static/*` (content-addressed by Next), **not** on `/data/*.dat`
   unless the filename is guaranteed unique. Since it is (`catalog.<hash>.dat`),
   keep `immutable` **only** for the exact hashed name and serve
   `public, max-age=300, must-revalidate` for anything else. Add a short
   `stale-while-revalidate` so a fresh deploy is picked up on the next visit.
4. **Do not cache 404s.** Cloudflare's `_headers` apply to error responses:
   a request to a _nonexistent_ path under `/_next/static/` returned `404` with
   `max-age=31536000, immutable` in testing. Scope cache rules so error
   responses get `no-store`.
5. **Sanity-check at runtime:** reject a catalogue whose row count drops by more
   than, say, 20% versus the previous load, or whose price bounds fall outside
   `[1, 10_000_000]`. Show a warning rather than silently rendering it.
6. **Deploy atomically:** upload the artifact first, then the HTML, or use a
   Cloudflare versioned deployment / `wrangler versions` so both switch
   together.

**Done when** a byte-flipped artifact fails closed with the existing error UI;
`curl -I` shows `must-revalidate` (not `immutable`) for a non-hashed data path;
a 404 under `/data/` is `no-store`; the deploy script uploads data before HTML.

### F-06 · The order message can be forged or edited · **Medium**

**CWE-74 / CWE-116 (Improper Neutralisation of Special Elements)**

**Where** `src/features/checkout/lib/order-message.ts:53` appends
`details.notes` verbatim after a `NOTES` heading. `notes` is capped at 1,000
characters (`constants.ts:9`) and allows newlines. Every other field is a
single-line input, so newlines cannot get in there — notes is the one hole.

**Evidence (executed)** With the notes field set to
`"ignore\n\nORDER------\norder subtotal: $0.001\nSHIPPING ADDRESS\n1 Attacker Way"`,
the generated message contains a **second full `ORDER------` block** with a
forged subtotal and address:

```
NOTES
ignore

ORDER------
order subtotal: $0.001
SHIPPING ADDRESS
1 Attacker Way
```

**How it is exploited**

This needs no tooling, just a text field:

1. A buyer assembles a large order.
2. In notes, they paste a second `ORDER------` block with a tiny subtotal and a
   different delivery address.
3. They copy the message and send it. A distracted operator reading a long
   Telegram message sees two blocks; whichever they process is a coin flip. If
   they process the cheap one, the goods ship at the wrong price to the wrong
   address.
4. Variant: the buyer simply **edits the copied text** before sending — nothing
   binds the message to the site's arithmetic. Totals, quantities and item
   names are advisory.

Related, smaller: an order has **no reference, timestamp or nonce**, so two
buyers sending similar carts produce near-identical messages, and neither party
can prove which message was sent when. That is the repudiation half of the same
problem.

**Impact** Financial (underpayment, mis-shipment) and operational (duplicate
orders). The ceiling is "whatever an inattentive operator will honour", which is
exactly why the design leans on human review. If the team ever stops
re-pricing every order manually, this becomes High.

**Remediation**

1. **Neutralise the channel:** before composing, replace `\r\n` and `\n` in
   notes with a space, collapse runs, and strip the delimiter token (`ORDER------`)
   and the marker lines (`order subtotal:`, `SHIPPING ADDRESS`, `ITEMS`,
   `NOTES`). A one-line `sanitizeMessageField()` used for _every_ interpolated
   value is enough; keep the raw value in the form state.
2. Or **quote** user text (`> ` prefix on each line) so it can never masquerade
   as structure.
3. **Add an order reference**: a short random code (e.g. `TIP-7F3K9Q`) plus a
   UTC timestamp, generated in the dialog and shown on screen. The team can then
   ask the buyer to repeat the code in a separate message, which breaks
   copy-paste forgery.
4. **Print a verification line**: `subtotal 1.330 USD · 3 line items · 20 units`
   computed once and repeated at the top and bottom, so a mismatch is visible.
5. **Tell the team, in writing, to re-derive prices from the catalogue before
   quoting.** This is already implied by the flow; make it explicit in the
   operations doc. It is the only real defence against an edited paste.
6. Consider a Telegram bot with a signed deep link if volume ever justifies it;
   a static site cannot produce an unforgeable message on its own.

**Done when** the fuzz case above produces a message with exactly one
`ORDER------` block; a newline in any field cannot begin a line that looks like
a marker; every message contains a visible reference code and timestamp.

### F-08 · `deploy.ps1` stages everything and pushes · **Low**

**CWE-538 (Insertion of Sensitive Information into Externally-Accessible File)**

**Where** `deploy.ps1:217` — `git add -A`, followed by `git commit` and
`git push`; `:142` runs `npm run catalog:build` first. No review of the staging
area, no `npm ci`, no audit, no tests, no signature.

**How it is exploited / what goes wrong** Not an attacker: a developer. Any file
in the working tree — a local `.env.local` variant if the ignore rules change, a

3. Run `npm ci`, `npm run lint`, `npm run typecheck`, `npm run build` and
   `npm audit --omit=dev` before committing; abort on failure.
4. Prefer a GitHub Action as the only thing that can deploy, with the Cloudflare
   token in repository secrets and no long-lived token on a laptop.
5. Sign release commits (`git commit -S`) so a pushed artifact can be traced to a
   human.

### F-09 · No `robots.txt` and no `X-Robots-Tag` · **Low**

**Where** `public/` contains no `robots.txt`; the export has none. `/checkout/`
carries `<meta name="robots" content="noindex, nofollow">`
(`src/app/checkout/page.tsx:7`), which works for the major engines but is a
page-level hint, not a header, and it is trivially ignored by scrapers.

**How it is exploited** Crawlers (including AI training crawlers) index 8,522
product rows and 700 manufacturers. That is business data you have chosen to
publish, but you may not want it mirrored by every aggregator, and you
certainly do not want `/checkout/` appearing in results with stale copy.

**Remediation**

1. Add `public/robots.txt` with `User-agent: *` / `Disallow: /checkout/` and,
   if desired, explicit groups for `GPTBot`, `CCBot`, `Google-Extended`,
   `anthropic-ai`, `PerplexityBot`.
2. Add to `_headers`:
   ```
   /checkout/*
     X-Robots-Tag: noindex, nofollow, noarchive
   ```
3. Keep the meta tag; defence in depth costs nothing.

**Done when** `/robots.txt` returns 200 with the rules and
`curl -I /checkout/` shows `x-robots-tag`.

### F-11 · Unbounded decompression and a 415 ms main-thread index build · **Low**

**Where** `load-catalog.ts:134-139` pipes the artifact through
`DecompressionStream` into `new Response(...).text()` with **no output cap**.
`src/features/catalog/lib/search.ts:78` builds the folded index lazily on first
query, on the main thread.

**Evidence (measured on the real artifact, Node 22, desktop-class CPU)**

- Cold index build: **415 ms** (one-off, on the first keystroke or first load of
  the explorer).
- Per-query search: **1.06–7.04 ms**, worst case a single-character query
  returning 8,416 matches.
- Filter pass over 8,416 rows: 0.13 ms.

**Why it matters** On a low-end Android phone the 415 ms becomes roughly
1–2 seconds of frozen UI at exactly the moment the visitor starts typing — a
usability defect that looks like a broken site. There is no cross-user DoS: the
cost is per device, so "load testing" here is a CPU budget, not concurrency. The
missing decompression cap matters only if the artifact becomes attacker-writable
(e.g. a poisoned build): a 200 KB `.dat` can expand to gigabytes and hang the
tab. Cloudflare's per-response limits do not protect the browser.

**Remediation**

1. Precompute the folded index at build time and ship it alongside (or inside)
   the artifact — the fold is deterministic, so this is pure latency removal.
2. Or move index construction into a Web Worker, keeping the UI thread free.
3. Check `response.headers.get("content-length")` and reject > 1 MB; while
   decompressing, count bytes and abort past a cap (e.g. 8 MB) using a
   `TransformStream`.
4. Reject catalogues with an implausible row count (e.g. > 50,000) with the
   existing corrupted-catalog state.

### F-12 · Messenger impersonation is the most plausible fraud route, and nothing counters it · **Low**

**Where** `src/features/checkout/components/order-dialog.tsx` tells the buyer to
send the message to `@tipind` (and shows a safety note); `src/config/site.ts`
renders the handle and `shop@tipind.ru` from env.

**How it is exploited** Register `@tipind_official`, `@tipind_support`,
`@tipindorders` or a Cyrillic-lookalike handle, then message buyers who have
posted about the site, or rely on typos. Payment is crypto, so a diverted order
is irreversible. The site's text warning helps, but a buyer who already has a
message window open will not re-read it.

**Remediation**

1. **Put the canonical handle in one place and keep it stable**; never change it
   without announcing it on the site first.
2. **Require the order reference** generated by the site (see F-06) in the first
   message, and **never** accept payment instructions in a chat the buyer
   initiated from a profile search.
3. **Publish a verification sentence** on the checkout dialog and in the email
   footer: "We will only ever message you from `@tipind`. We will never ask you
   to send funds to a different handle."
4. **Squat the obvious variants** yourself if Telegram allows, and monitor.
5. Add the handle to the site's structured data (`Organization.sameAs`) so
   search results point at the right one.

### F-13 · Missing defence-in-depth headers; header rules also apply to errors · **Low**

**Where** `public/_headers`. Present: `X-Content-Type-Options`,
`X-Frame-Options: DENY`, `Referrer-Policy`, `Strict-Transport-Security`,
`Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`. Missing:
`Content-Security-Policy` (F-02), `Cross-Origin-Embedder-Policy`,
`Cross-Origin-Resource-Policy`, `X-Permitted-Cross-Domain-Policies`,
`Permissions-Policy` coverage for `browsing-topics`/`interest-cohort`
(privacy), and `X-Robots-Tag` on checkout (F-09). Also: HSTS has no
`includeSubDomains`/`preload`, and the `_headers` wildcard rules are applied to
**404 responses** — a request to a nonexistent path under `/_next/static/`
returned `Cache-Control: public, max-age=31536000, immutable` with a 404 body.

**Remediation**

1. Add `Cross-Origin-Resource-Policy: same-origin` and
   `Cross-Origin-Embedder-Policy: require-corp` once you have confirmed the page
   loads no cross-origin subresources (it currently loads none, so this is safe
   and would break nothing).
2. Add `browsing-topics=(), interest-cohort=()` to `Permissions-Policy`.
3. Consider `includeSubDomains` on HSTS if you control the whole zone (on
   `workers.dev` you do not — skip).
4. Scope cache headers so they do not apply to 4xx/5xx, or add
   `Cache-Control: no-store` for error paths.
5. Re-run [the header check](./evidence.md#2-live-header-and-cache-behaviour)
   after every deploy; header drift is silent otherwise.

### F-14 · The XOR "masking" is not encryption · **Info**

**Where** `src/features/catalog/lib/load-catalog.ts:110-131`, key in

**Reality** Anyone can decode the catalogue in ten lines, and the key has been

the payload small), keep the comment that says so, and make sure nobody adds
"internal" fields to the build output on the assumption that the mask protects
them.

## 5. Controls that are already right (do not regress these)

Worth stating explicitly, because they are the reason this review is short:

- **No injection sinks.** Zero `dangerouslySetInnerHTML`, `innerHTML`, `eval`,
  `new Function`, `document.write`, `postMessage`. Every external link has
  `rel="noreferrer"`.
- **One network call.** `load-catalog.ts:151`, same-origin, `credentials:
"omit"`, `cache: "force-cache"`. No third-party origins in any exported HTML
  (the only absolute URLs are `w3.org` namespaces, your own domain, and `wa.me`
  links).
- **No cookies, no analytics, no beacons, no fonts from Google.** Nothing to
  consent to, nothing to leak to an ad network.
- **`localStorage` is treated as hostile.** Cart and checkout both sanitise on
  read with size caps (100 KB), version checks, quantity clamps (1–9,999), line
  caps (500) and per-field length caps. Fuzzing with wrong versions, bad JSON,
  2 MB payloads, `Infinity`, `NaN`, floats, `__proto__` keys and 5,000 duplicate
  lines produced no crash and no prototype pollution.
- **`__proto__` / prototype pollution:** not exploitable through either parser.
- **No ReDoS.** The packaging regex (the one the code comments claim is linear)
  was stress-tested with 1,000-character adversarial inputs: worst case 0.17 ms.
- **Checkout cannot be submitted with invalid data** — `validateDetails` gates
  the dialog, including a real email check and per-country postcode rules.
- **No source maps** in the export; `/checkout/` is `noindex`; contact details
  are deliberate.
- **Headers are set from source** (`public/_headers`), so they are reviewable in
  git rather than living only in a dashboard.

## 7. Retest protocol

When you have applied a fix and it does not look right:

1. Re-run the matching check in
   [remediation-plan.md § Retest checklist](./remediation-plan.md#retest-checklist)
   and paste the output.
2. State **what changed** (file, header, deployment, commit) and **what you
   expected** versus **what you saw**.
3. If a header or CSP is involved, also paste the response headers for `/`,
   `/checkout/` and `/data/*.dat` — differences between paths are usually the
   cause.
4. Re-run the parser fuzz harness (`docs/security/evidence.md` §4) whenever a
   sanitiser or store changes; it needs only Node.

No fix will make a static site with a public price list "fully secure" — the
goal is that the remaining risks are known, small, and owned. That is achievable
here, and the list above is short enough to finish.
